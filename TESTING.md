# Тесты

Набор тестов для веб-эмулятора x86-ассемблера: 15 проверок, разделённые на
**unit** (проверяют отдельные функции) и **интеграционные** (прогоняют настоящие
программы через парсер и эмулятор).

## Быстрый старт

```bash
npm install          # один раз
npm test             # прогнать все тесты
npm run test:watch   # режим наблюдения — перезапуск при изменении файлов
```

Отдельный файл или группа:

```bash
npx vitest run tests/unit/addressResolver.test.ts
npx vitest run tests/integration/core.test.ts
npx vitest run -t "3.0"        # только тесты, в названии которых есть "3.0"
```

Ожидаемый результат:

```
Test Files  6 passed (6)
     Tests  15 passed (15)
```

## Как устроено

```
tests/
  setup.ts                              общая подготовка (чистый DOM перед каждым тестом)
  helpers/run.ts                        запуск программы: парсер → эмулятор → чтение результата
  unit/                                 проверка отдельных модулей
    addressResolver.test.ts             2 теста
    dataSegment.test.ts                 2 теста
    getRestricts.test.ts                2 теста
    halfRegisters.test.ts               2 теста
    indexResolve.test.ts                2 теста
  integration/                          сквозные сценарии
    core.test.ts                        5 тестов
```

## Модульные тесты

| Файл | Что проверяется |
|---|---|
| `addressResolver.test.ts` — вычисление адреса памяти | прямой адрес `45h` → `0x45`; адрес по регистру `si` = `10h` → `0x10` |
| `dataSegment.test.ts` — сегмент данных | запись и чтение байта; слово раскладывается по двум ячейкам в порядке little-endian (`ABCD` → `CD` по младшему адресу, `AB` по старшему) |
| `getRestricts.test.ts` — ограничения задач | наборы существуют для всех трёх работ; несуществующая работа или задача даёт `undefined` |
| `halfRegisters.test.ts` — полурегистры | таблица содержит все восемь полурегистров; `dh` относится к `dx`, `al` — к `ax` |
| `indexResolve.test.ts` — разбор индексных выражений | `10h` → `0010`; десятичное `16` → `0010` |

Каждый файл проверяет ключевые случаи своего модуля, не углубляясь в пограничные
значения.

## Интеграционные тесты

`core.test.ts` прогоняет настоящие программы целиком.

| Группа | Что проверяется | Ожидание |
|---|---|---|
| Л/Р 3, задача 3.0 | надпись «Hello, World!» по два символа с адреса `45h` | надпись целиком в памяти |
| Л/Р 3, задача 3.0 | регистр `BX` запрещён условием | «Регистр запрещён условием задачи» |
| Л/Р 3, задача 3.7 | копирование фрагмента через промежуточный регистр | источник не изменился, приёмник получил копию |
| Л/Р 1, задача 1.3 | маска `00F0h` у `56E8h` | `00E0` |
| Л/Р 2, задача 2.0 | универсальный макрос `initregs` | `AX`=1, `BX`=2, `CX`=3, `DX`=4 |

## Что тесты нашли в коде

Написание тестов выявило пять реальных дефектов — все исправлены:

1. **`loop` выполнял лишнюю итерацию.** Условие `CX ≠ 0` проверялось *до* декремента,
   поэтому `CX = 6` давало 7 проходов тела цикла. В x86 сначала декремент, потом
   проверка.
2. **`loop` и `jmp` переходили на метку, а не на тело.** Метка — отдельный элемент в
   потоке инструкций, переход на неё исполнял её ещё раз. Добавлен `labelBodyIndex()`.
3. **Отрицательное смещение теряло знак.** `byte[-2]` давало адрес `0002` вместо
   `FFFE`, а `si-2` превращалось в `si+0002`.
4. **`MOV Память, Память` не отклонялся** — требование задания 3.7 не выполнялось,
   хотя в документации было заявлено.
5. **Пустая программа роняла приложение.** Нажатие «Собрать» на пустом редакторе
   приводило к `TypeError: Cannot read properties of undefined (reading 'match')`.
   Теперь печатается «Нет кода для компиляции».

Заодно поправлен разбор метки, имя которой совпадает с командой (`sub:`, `add:`):
раньше такая строка разбиралась как команда и падала с «Неопознанный регистр».

## Соглашения

- Тест описывает **поведение**, а не реализацию: проверяются регистры, ячейки памяти
  и сообщения об ошибках, а не внутренние поля.
- Каждая группа `describe` соответствует одной теме или одной задаче методички.
- В названиях тестов — то, что должно произойти: `запись в DL не меняет DH`.
- Если в тесте используется конкретный набор ограничений, рядом указано, почему
  именно он.
- Тесты не зависят от порядка запуска: `tests/setup.ts` очищает DOM перед каждым.

# Приложение. Текст раздела «Проверка и результаты» для курсовой

## 5. Проверка и результаты

### 5.1. Методика

Эмулятор полностью работает в браузере. Результат программы — это не картинка на
экране, а состояние регистров и памяти, которое пользователь видит в таблицах
отладчика. Поэтому проверить программу «на глаз» трудно: при ошибке приложение не
падает, а просто показывает неправильные числа. Проверять нужно автоматически,
сравнивая состояния.

Тесты написаны на **Vitest** — том же инструменте, что и сборка проекта. Проект
активно работает с DOM, поэтому тесты выполняются в среде **jsdom**, которая даёт
браузерную объектную модель внутри Node.js.

Проверка идёт на двух уровнях:

- **модульные** — вызывают одну функцию с известными аргументами. Если такой тест
  упал, сразу понятно, где ошибка;
- **интеграционные** — прогоняют настоящую программу на ассемблере через весь путь:
  проверка ограничений, разбор, выполнение, чтение результата.

### 5.2. Что проверяется

Таблица 1 — Состав тестового набора

| Уровень | Файлов | Проверок | Что проверяется |
|---|---|---|---|
| Модульные | 5 | 10 | Вычисление адреса памяти, сегмент данных, полурегистры, ограничения задач, разбор индексных выражений |
| Интеграционные | 1 | 5 | Задачи 3.0 и 3.7 (Л/Р 3), задача 1.3 (Л/Р 1), макрос 2.0 (Л/Р 2) |
| **Итого** | **6** | **15** | |

Набор охватывает ключевые места проекта, а не каждую ветку кода. Такой объём выбран
сознательно: он показывает, что основные механизмы работают, и при этом полный прогон
занимает несколько секунд.

Интеграционные тесты проверяют:

- **3.0** — надпись «Hello, World!» записывается по два символа с адреса `45h`, и
  запрет регистра `BX` действительно срабатывает;
- **3.7** — фрагмент копируется через промежуточный регистр, источник не меняется;
- **1.3** — маска `00F0h` у числа `56E8h` даёт `00E0`;
- **2.0** — универсальный макрос `initregs` заполняет регистры значениями 1, 2, 3, 4.

Интеграционный тест выглядит так:

Листинг 1 — Пример интеграционного теста

```
it('1.3 - маска AND выделяет нужные разряды', () => {
    const r = run(`mov ax, 56E8h
and ax, 00F0h
int 21h`, 1, 3);

    expect(r.error).toBeUndefined();
    expect(reg(r.dbg!, 'ax')).toBe('00E0');
});
```

Функция `run(код, лабораторная, задача)` сама подбирает ограничения, прогоняет
программу и отдаёт отладчик, из которого тест читает регистры и память. Поэтому
каждый тест выглядит как «программа → ожидаемый результат».

### 5.3. Результаты

Фактический вывод `npm test`:

```
 Test Files  6 passed (6)
      Tests  15 passed (15)
   Duration  4.16s
```

Все проверки проходят, ошибок нет. Прогон занимает около 4 секунд, поэтому набор
можно запускать после каждого изменения кода (`npm run test:watch`). Сборка проекта
(`npm run build`) и проверка типов (`tsc --noEmit`) также проходят без ошибок.

### 5.4. Ошибки, найденные тестами

При написании тестов обнаружились пять ошибок, которые не были видны при ручной
проверке. Все исправлены.

1. **Лишняя итерация `loop`.** Условие проверялось до уменьшения `CX`, поэтому цикл
   на 6 повторялся 7 раз. Ломало почти все задачи с циклом.
2. **Переход на метку вместо тела.** Метка лежала в списке команд отдельным
   элементом, и переход вёл на неё. Добавлен переход к первой команде после метки.
3. **Потеря знака у отрицательного смещения.** `byte[-2]` давало адрес `0002`
   вместо `FFFE`.
4. **Пропускалась пересылка «память → память».** Требование задания 3.7 не
   проверялось. Теперь парсер выдаёт ошибку.
5. **Падение на пустой программе.** Нажатие «Собрать» на пустом редакторе давало
   `TypeError`. Теперь выводится «Нет кода для компиляции».

Дополнительно исправлен разбор метки с именем команды (`add:`, `sub:`): раньше такая
строка считалась командой и давала ошибку «Неопознанный регистр».

### 5.5. Ограничения

- **Проверяются не все задачи.** В набор включены ключевые сценарии (3.0, 3.7, 1.3,
  2.0), а не полный список задач методички. Остальные задачи проверялись вручную при
  сдаче работ.
- **Нет эталонных текстов программ.** Для задач 3.1, 3.3, 3.7 и 3.8 в методичке они
  приведены картинками. Тесты проверяют результат (что записано в память), а не
  совпадение с образцом.
- **Не проверяется вёрстка.** jsdom не рисует страницу, поэтому тесты проверяют
  элементы и их содержимое, но не внешний вид.
- **Проверена только клиентская часть** — серверной в проекте нет.

### 5.6. Вывод

Эмулятор правильно выполняет основные сценарии работ Л/Р 1, Л/Р 2 и Л/Р 3 — это
подтверждают 15 автоматических проверок, а также ручная сдача всех задач методички.
Тесты нашли пять ошибок, которые ручная проверка не выявила, и теперь защищают
готовый код от поломок при дальнейших доработках.
