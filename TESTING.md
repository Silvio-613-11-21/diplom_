# Тесты

Набор тестов для веб-эмулятора x86-ассемблера: 237 проверок, разделённые на
**unit** (проверяют отдельные функции) и **интеграционные** (прогоняют настоящие
программы через парсер и эмулятор, вплоть до интерфейса страницы).

## Быстрый старт

```bash
npm install          # один раз
npm test             # прогнать все тесты
npm run test:watch   # режим наблюдения — перезапуск при изменении файлов
```

Отдельный файл или группа:

```bash
npx vitest run tests/unit/addressResolver.test.ts
npx vitest run tests/integration/lab3-tasks.test.ts
npx vitest run -t "3.0"        # только тесты, в названии которых есть "3.0"
```

Ожидаемый результат:

```
Test Files  11 passed (11)
     Tests  237 passed (237)
```

```

  helpers/run.ts                        запуск программы: парсер → эмулятор → чтение результата
  unit/                                 проверка отдельных модулей
```

### Конфигурация

`vitest.config.ts` повторяет алиасы путей из `vite.config.ts` (`src/…`, `shared/…`,
`entities/…` и т.д.), поэтому тесты импортируют модули так же, как основной код.
Окружение — **jsdom**, потому что почти весь проект работает с DOM: `DataSegment` и
`CodeSegment` строят таблицы, `Debugger` создаёт виджеты, `Registers` обновляет ячейки.

### Хелпер `tests/helpers/run.ts`

Главный инструмент интеграционных тестов. Принимает текст программы и номер
задачи, сам достаёт ограничения, компилирует, выполняет и возвращает результат:

```ts
const r = run(`mov word[45h], 'He'
int 21h`, 3, 0);

r.error          // строка, если программа не собралась
r.dbg            // отладчик: регистры, флаги, память
r.instructions   // сколько инструкций получилось

memText(r.dbg, 0x45, 0x52)   // "Hello, World!" — текст из памяти
reg(r.dbg, 'ax')             // значение регистра
```

Внутри — настоящие `parser`, `Emulator` и `Debugger`, никаких заглушек. Есть защита
от зависания: не более 20 000 шагов на программу. Отдельно есть `compile()` — только
собрать программу, без выполнения (нужно для проверки ошибок компиляции).

## Unit-тесты

### `addressResolver.test.ts` — вычисление адреса памяти

Проверяет функцию `resolveAddress(выражение, регистры)`: превращает содержимое
`byte[...]` / `word[...]` в линейный адрес `0..FFh`.

| Группа | Что проверяется |
|---|---|
| Прямые адреса | `45h`, `4Fh`, `10`, `1010b`, границы `0` и `FFh`, лишние пробелы |
| Косвенная адресация | `si`, `bx`, `si+2`, `bx+si`, `bx+si+4`, полурегистры `bh`/`bl`, вычитание `si-1` |
| Границы сегмента | адрес `100h` отвергается; регистр, уводящий за границу (`si=F5h`, `+10h`); пустое выражение; мусор; несуществующий регистр |
| `parseNumber` | `1Ah`, `FFh`, `1010b`, число без суффикса как hex, пустая строка, мусор |

Отдельный тест фиксирует архитектурное решение: `resolveAddress` сама по себе —
низкоуровневая и складывает любые регистры, а недопустимый `dx` в адресе отсекает
уровень выше (`IndexResolve`) — тест прогоняет полный конвейер и ждёт «Ошибка в индексе».

### `indexResolve.test.ts` — разбор адресного выражения

| Группа | Что проверяется |
|---|---|
| Прямые адреса | `10h` → `0010`, десятичное `16` → `0010`, двоичное → `000a`, ноль |
| Косвенная адресация | одиночный регистр; **порядок «база + индекс»** (`si+bx` → `bx+si`); смещение с суффиксом `h`; база + индекс + смещение; полурегистры как база |
| Отрицательные смещения | `si-2` → `si+fffeh`, `-2` → `fffe`, `-2` и `0-2` дают одно и то же. **Регресс на два исправленных бага:** раньше терялся знак у одиночного числа и у регистра |
| Недопустимые выражения | два базовых регистра, два индексных, три регистра, умножение регистра, деление на ноль, мусор, пустая строка |
| Арифметика | приоритет умножения над сложением, вычитание, целочисленное деление, смешанные системы счисления (`10h+1+10b` → `0013`) |

### `regexp.test.ts` — обработка текста программы

Парсер приводит код к нижнему регистру и убирает пробелы, но **содержимое кавычек
меняться не должно**. Все преобразования идут через `transformOutsideQuotes`.

| Группа | Что проверяется |
|---|---|
| `transformOutsideQuotes` | преобразуется только код вне кавычек; регистр внутри строки сохраняется; несколько строк в одной строке кода; незакрытая кавычка не ломает обработку; пустая строка |
| `delComments` | комментарий после кода удаляется; `;` внутри строки сохраняется (`'a;b'`, `';'`) |
| `delSpace` | пробелы удаляются из кода; **ведущий и хвостовой пробелы внутри строки сохраняются** (`' W '`) |
| `toLowerCase` | команды и регистры приводятся к нижнему регистру; `'Hello, World!'` и `'A'` не меняются |
| `lineIsEmpty` | пустая строка, строка из пробелов и табуляции, строка с кодом |
| Защита от некорректного входа | `extractSegmentName` и `org100hCheck` не падают на `undefined`; распознавание `codesegment.data` и `org100h` |
| Комплексный сценарий | строка из задания 3.0 проходит все три преобразования подряд и остаётся `'He'` |

## Что тесты нашли в коде

Написание тестов выявило четыре реальных дефекта — все исправлены:

1. **`loop` выполнял лишнюю итерацию.** Условие `CX ≠ 0` проверялось *до* декремента,
   поэтому `CX = 6` давало 7 проходов тела цикла. В x86 сначала декремент, потом
   проверка. Ломало все задачи с `loop` в Л/Р 1 и почти все задачи Л/Р 3.
2. **`loop` и `jmp` переходили на метку, а не на тело.** Метка — отдельный элемент в
   потоке инструкций, переход на неё исполнял её ещё раз. Добавлен `labelBodyIndex()`.
3. **Отрицательное смещение теряло знак.** `byte[-2]` давало адрес `0002` вместо
   `FFFE`, а `si-2` превращалось в `si+0002`. Причина — знак первого операнда не
   учитывался при сведении выражения.
4. **`MOV Память, Память` не отклонялся** — требование задания 3.7 не выполнялось,
   хотя в документации было заявлено. Теперь парсер выдаёт понятную ошибку.
5. **Пустая программа роняла приложение.** Нажатие «Собрать» на пустом редакторе
   приводило к `TypeError: Cannot read properties of undefined (reading 'match')`:
   парсер проверял директивы `segment`/`org 100h` по первой строке, а её нет.
   Теперь печатается «Нет кода для компиляции».

Заодно поправлен разбор метки, имя которой совпадает с командой (`sub:`, `add:`):
раньше такая строка разбиралась как команда и падала с «Неопознанный регистр».

## Соглашения

- Тест описывает **поведение**, а не реализацию: проверяются регистры, ячейки памяти
  и сообщения об ошибках, а не внутренние поля.
- Каждая группа `describe` соответствует одной теме или одной задаче методички.
- В названиях тестов — то, что должно произойти: `запись в AH не меняет AL`.
- Если в тесте используется конкретный набор ограничений, рядом указано, почему
  именно он: `// набор 1.8: mov, loop, shl, inc, int`.
- Тесты не зависят от порядка запуска: `tests/setup.ts` очищает DOM перед каждым.

## 5. Проверка и результаты

### 5.1. Методика проверки

Разработанный программный продукт — веб-эмулятор x86-ассемблера, выполняющийся
полностью на стороне клиента. Эмулятор реализован на TypeScript с использованием
сборщика Vite и архитектуры Feature-Sliced Design. Особенность предметной области
состоит в том, что результат работы программы — не визуальный вывод, а **состояние
регистров и памяти**, которое пользователь наблюдает через таблицы отладчика.
Ошибка в вычислении адреса или в порядке выполнения команды не приводит к падению
приложения, а даёт неверное, но внешне правдоподобное значение. Именно поэтому
проверка сводится к автоматизированному контролю состояний, а не к визуальному
осмотру интерфейса.

Для проверки выбран фреймворк **Vitest** — он работает в той же среде Node.js, что и
сборщик Vite, использует те же алиасы путей и не требует отдельного
конфигурационного файла для сборки. Поскольку значительная часть проекта
взаимодействует с DOM (таблицы памяти и регистров, отладочные виджеты, обработчики
кнопок), тесты выполняются в окружении **jsdom**, предоставляющем браузерную
объектную модель в Node.js.

Проверка ведётся на двух уровнях.

**Модульные (unit) тесты** изолируют отдельную функцию или класс и подают на вход
заранее известные значения. Они позволяют точно указать место дефекта: если падает
тест `IndexResolve`, причина находится в вычислении адреса, а не в парсере или
эмуляторе.

**Интеграционные тесты** прогоняют настоящие программы на ассемблере через полный
путь обработки: проверка ограничений задачи → лексический разбор → построение
списка инструкций → пошаговое выполнение → чтение результата. Эти тесты отвечают на
вопрос, работает ли продукт в целом, тогда как модульные — на вопрос, верна ли
конкретная функция.

Верхний уровень составляют **сквозные тесты интерфейса**: они работают с реальным
DOM страницы — вводят текст в редактор, нажимают кнопки «Собрать» и «Выполнить всё»
и читают значения из таблиц регистров и памяти. Это единственная группа тестов,
проверяющая продукт так, как его видит пользователь.

### 5.3. Организация испытаний

Для интеграционных тестов реализован вспомогательный модуль `tests/helpers/run.ts`,
который принимает текст программы и номер лабораторной работы с номером задачи,
самостоятельно подбирает ограничения через `getRestrists` и прогоняет программу до
останова. Это позволило записывать каждый тест в виде «программа — ожидаемый
результат» без повторения служебного кода (листинг 1).

Листинг 1 — Пример интеграционного теста

```
it('1.3 - маска AND выделяет нужные разряды', () => {
    const r = run(`mov ax, 56E8h
and ax, 00F0h
int 21h`, 1, 3);

    expect(r.error).toBeUndefined();
    expect(reg(r.dbg!, 'ax')).toBe('00E0');
});
```

Тест читается как постановка задачи: исходное значение `56E8h`, маска `00F0h`,
ожидаемый результат `00E0h`. Проверяется наблюдаемый результат — значение регистра,
а не внутреннее состояние структур данных.

Модульные тесты построены по тому же принципу: проверяется поведение, а не
реализация (листинг 2).

Листинг 2 — Пример модульного теста

```
it('запись в DL не меняет DH', () => {
    const r = new TestRegisters();
    r.setFull('dx', '0A00');
    r.setFull('dl', '05');

    expect(r.getValueByName('dx')).toBe('0A05');
});
```

Тест фиксирует правило предметной области: полурегистр адресует половину
16-битного регистра, и запись в младший байт не должна затрагивать старший.

При выполнении программы установлен предел в 20 000 шагов
(`MAX_STEPS` в `run.ts`). Это защита от зацикливания: при ошибке в реализации
цикла тест завершается с диагностикой, а не зависает.

### 5.6. Дефекты, выявленные при испытаниях

Автоматизированная проверка выявила пять дефектов, не обнаруженных при ручном
тестировании. Все дефекты исправлены, после исправления набор проходит полностью.

**Дефект 1. Лишняя итерация цикла `loop`.** Условие `CX ≠ 0` проверялось до
декремента, поэтому при `CX = 6` тело цикла исполнялось семь раз. В архитектуре x86
декремент выполняется первым. Дефект затрагивал все задачи Л/Р 1 с циклом и
практически все задачи Л/Р 3.

**Дефект 2. Переход на метку вместо тела.** Метка хранилась в потоке инструкций как
отдельный элемент, и переход `loop`/`jmp` вёл на неё, а не на первую команду после
метки. Метка исполнялась повторно — как правило, без видимого эффекта, но при
вложенных переходах приводило к смещению адресов возврата.

**Дефект 3. Потеря знака отрицательного смещения.** Выражение `byte[-2]` давало адрес
`0002` вместо `FFFE`, а `si-2` превращалось в `si+0002`. Причина — при сведении
выражения не учитывался знак первого операнда.

**Дефект 4. Не отклонялась пересылка «память → память».** Требование задания 3.7
использовать промежуточный регистр фактически не проверялось, хотя было заявлено в
документации. Теперь парсер выдаёт сообщение «Пересылка из памяти в память запрещена
— нужен промежуточный регистр».

**Дефект 5. Отказ при пустой программе.** Нажатие «Собрать» на пустом редакторе
приводило к необработанному исключению `TypeError: Cannot read properties of
undefined (reading 'match')`: парсер обращался к первой строке программы, не проверяя
её наличие. Дефект выявлен появлением сообщения об ошибке в выводе тестов — сам
интерфейс при этом оставался работоспособным, что затрудняло обнаружение при ручной
проверке. Теперь выводится сообщение «Нет кода для компиляции».

Дополнительно исправлен разбор метки, имя которой совпадает с именем команды
(`add:`, `sub:`): ранее такая строка воспринималась как команда и завершалась
ошибкой «Неопознанный регистр».

### 5.7. Выявленные ограничения

**Ограничение 1. Проверка по методичке, а не по эталонным программам.** Для задач
3.1, 3.3, 3.7 и 3.8 текст программы-образца в методичке опубликован в виде
изображения и не может быть прочитан машинно. Тесты для этих задач построены на
воспроизведении требования задания и проверке наблюдаемого результата (заполнение
области памяти, длина надписи, счётчик вхождений), а не на посимвольном сравнении с
эталоном. Это допускает расхождение в способе решения при совпадении результата.

**Ограничение 2. Сквозные тесты не проверяют вёрстку.** Тесты интерфейса работают в
jsdom, который предоставляет объектную модель документа, но не выполняет
вычисления стилей и отрисовку. Следовательно, проверяется наличие элементов,
обработка событий и содержимое таблиц, но не внешний вид страницы, расположение
блоков и корректность отображения в конкретном браузере.

**Ограничение 3. Отсутствие нагрузочных испытаний.** Эмулятор выполняет программы
учебного размера — десятки команд, предел в 20 000 шагов. Производительность на
программах большого объёма и поведение при длительном непрерывном выполнении не
исследовались, поскольку такие сценарии выходят за рамки учебного назначения
продукта.

**Ограничение 4. Проверка только клиентской части.** Эмулятор полностью выполняется
в браузере и не имеет серверной составляющей, поэтому испытания ограничены одним
уровнем — клиентским приложением. Вопросы сетевого взаимодействия, разграничения
доступа и серверной валидации в данной работе не рассматривались ввиду отсутствия
соответствующих компонентов.
